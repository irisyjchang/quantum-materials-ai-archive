# Stage log runs

Work on the PDF or batch the operator specifies. Use `test.sqlite` for Test and `archive.sqlite` for Archive. Run the staging commands from the repository root. Use `.venv/bin/python` when the repository has a `.venv` folder (set it up with `python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt`); the command lines below write `python` for short. Save packets in the selected environment's review workspace and keep them and the source PDFs out of Git.

Use the [review and extraction rules](../../../DESIGN-MVP.md#5-log-run-review-and-extraction) and [JSON packet format](../../../.kiro/specs/local-growth-log-mvp/design.md#json-packet-format). Set `schema_version` to `1`, `prompt_version` to `stage-log-runs-v2`, and `model` to the model name reported by Codex or supplied by the operator. Never leave `model` or `prompt_version` blank.

Resolve the local source PDF from the operator's path or Drive reference and identify its archive filename. Run `python tools/lookup_drive_id.py <archive_filename>` before assessing a new source. If lookup exits nonzero, stop for that PDF and report the error. Compute the SHA-256 `file_hash` from the exact PDF bytes you inspect. Use the resulting `drive_file_id` and `file_hash` in both packets.

## Assess and route the PDF

1. Inspect the measurement table on all relevant pages. Use the upper Calculated table when present and ignore the lower table. Read headers, margins, and notes for context. Identify the runs and their page and row locations. If a run spans pages, retain all relevant locations.
2. Check whether every run can be tied to a source location, has at least one usable lookup value (researcher name, date or month, or JC identifier), and has interpretable stoichiometry. Treat a specific issue as critical if a run has no usable lookup value, the source location could attach values to the wrong run, or its stoichiometry is missing or ambiguous. Use uncertain when the scan leaves you unable to complete a reliable assessment, such as when cropping obscures which rows need assessment. A missing JC can be acceptable when another lookup value is available. If any run has a critical or uncertain issue, hold the whole PDF, including its readable runs.
3. Save a risk JSON packet with `stage` set to `risk`, the `decision`, and the `issues` array. Use `non_critical` when extraction can proceed, `critical` when any run has a critical issue, and `uncertain` when the PDF cannot be reliably assessed. Record each issue and its source location when known. Issues confined to the lower table do not raise the risk tier. Call `python staging.py risk-assess <packet.json> --source-pdf <local path> [--acceptance-run] <database.sqlite>` to register the version, retain the assessed PDF, and record the result. On exit 0, report the staging result. On a nonzero exit or if the tool is unavailable, keep the saved packet, report the blocker, and stop that PDF; never claim the assessment was recorded. If the tool reports that the PDF is reserved for the acceptance run, stop and ask the operator for a non-reserved PDF.
4. Before extracting, run `python staging.py check-gate <drive_file_id> <file_hash> <database.sqlite>`. On exit 0, use the retained PDF path printed after `cleared` and confirm its SHA-256 still matches `file_hash`. On nonzero exit or a hash mismatch, report the reason and produce zero extraction packets for that PDF. If it is held, report the issue, location, and what would resolve it. After clearance, resume with the same ID and hash and call `check-gate` again without replacing the assessment. A replacement scan needs its own assessment.

## Extract and stage drafts

1. Read the retained PDF returned by `check-gate`. Produce an extraction JSON packet with `stage` set to `extraction` and one entry per run in `runs`. Give each run a `draft_id` derived from the source version and its first measurement row so retries reuse the ID and distinct versions get distinct IDs. Include all relevant `source_locations`. Use 1-based PDF pages and count measurement-table rows from 1, skipping the header. Keep duplicate or partial JC values as written.
2. Preserve original formula, ratios, quantities, units, and basis where recorded. Keep any normalized or derived value separate from the transcription and show its evidence or calculation. Distinguish absent, illegible, ambiguous, inferred, and derived values with the packet's field statuses. Carry forward optional uncertainty and flag any critical issue discovered during extraction.

   Preserve a legible written `x`, including zero. When `x` is blank, calculate it if the documented composition or substitution basis and quantities determine a unique value. For a site fraction, divide an explicit substitution percentage by 100 or divide the substituent's molar amount by the total molar amount on that site. For elemental masses, convert units to grams and calculate moles with `n = mass / molar mass` using the [CIAAW reference table](https://ciaaw.org/abridged-atomic-weights.htm), then apply the documented basis. Use the amounts and species for the relevant site. Excess flux or transport agent belongs in the calculation only when the definition of `x` includes it.

   Put the result in `measurements.value.derived_x` with `status: "derived"`, the numeric `value`, and `evidence` that gives the page and row, inputs and units, basis, calculation, and reference weights when used. Preserve any other measurements and their original status. If the calculation is the only measurement, use `derived` for the enclosing field and leave its `raw_value` null. If the basis or inputs do not determine `x`, leave it blank and explain why in the measurement evidence. A missing `x` alone never prevents extraction or approval.

3. Save the extraction packet and call `python staging.py stage-drafts <packet.json> [--acceptance-run] <database.sqlite>`. Add `--acceptance-run` to the assessment and staging commands only when the operator explicitly identifies a formal acceptance run in Test. On exit 0, report the command's result, including the number of new drafts. If either command fails or is unavailable, keep the completed packet, report the error, and stop that PDF. Never claim drafts were staged without a successful command result.
4. Report the outcome for each PDF: held before extraction (with reason), drafts staged for review (with count), already staged, or technical failure (with the error). Newly staged drafts appear as Pending review in the app. If a critical issue first appears during extraction, stage the draft with that issue flagged in its field statuses and evidence, and report it; the reviewer holds that draft in the review app. The skill does not hold drafts itself. Only an authorized human reviewer can resolve critical issues, verify the source location, lookup value, and stoichiometry, and approve a run for search.

Example invocation: `$stage-log-runs Assess <PDF path or Drive reference> in Test and stage any eligible drafts for review.`
